# P3 代码讲解

本文用于梳理 Project3 的关键执行路径，目标是回答三个问题：

1. 系统从启动到 shell 的顺序是什么。
2. 进程创建、调度切换、syscall 返回是怎样闭环的。
3. 锁、屏障、条件变量、信号量、邮箱以及 exec/argv 传递如何衔接。

文中统一使用“触发条件 -> 跳转依据 -> 下一站”的结构描述。

## 1. 涉及的核心源码

主要文件如下：

- `init/main.c`：内核初始化入口，完成任务表、PCB、锁、异常、系统调用、屏幕、SMP 等初始化。
- `arch/riscv/kernel/entry.S`：异常入口、上下文保存/恢复、`switch_to`、`ret_from_exception`。
- `kernel/sched/sched.c`：调度器、进程创建、阻塞/唤醒、`do_exec`、`do_exit`、`do_waitpid` 等。
- `kernel/locking/lock.c`：自旋锁、互斥锁、屏障、条件变量、信号量、邮箱。
- `kernel/syscall/syscall.c`：系统调用分发器。
- `tiny_libc/syscall.c`：用户态系统调用封装。
- `arch/riscv/crt0/crt0.S`：用户程序启动入口 `_start`，负责调用 `main()`。
- `test/shell.c`：shell 解析命令并调用 `sys_exec`。
- `test/test_project3/*.c`：具体用户程序，例如 `add`、`multicore`、`barrier`、`condition`、`mbox_client`、`mbox_server`。

## 2. 从上电到 shell 的完整流程

系统的最外层执行顺序是：

1. U-Boot 启动。
2. 输入 `loadboot`，把内核镜像加载到内存。
3. 进入内核 `main()`，执行 `init/main.c` 中的初始化逻辑。
4. `init_task_info()` 建立任务名到镜像编号的映射。
5. `init_pcb()` 或当前代码中的 `init_idle_pcbs()` / `init_pcb_stack()` 负责准备初始 PCB 和空闲任务的内核栈。
6. `init_locks()`、`init_exception()`、`init_syscall()`、`init_screen()` 完成运行环境初始化。
7. 开启时钟中断和抢占后，调用 `do_scheduler()`，把第一个可运行任务切到 CPU 上。
8. 当前工程启动后进入的是 shell 进程，shell 再通过 `exec` 触发后续测试程序。

这个过程里最关键的一点是：**内核并不是直接跳到用户程序，而是先把 PCB、内核栈、用户栈、寄存器上下文都准备好，再通过调度器和异常返回机制进入用户态。**

### 2.1 启动链的跳转依据

触发条件 -> 跳转依据 -> 下一站：

1. 条件
- U-Boot 已经把内核镜像装入内存。

2. 依据
- `init/main.c` 的 `main()` 开始执行，顺序调用初始化函数。

3. 下一站
- 先完成 PCB、任务表、锁、异常、系统调用、屏幕、SMP 初始化，再进入调度器。

## 3. 任务 1：进程创建与调度

### 3.1 PCB 和上下文的关系

`include/os/sched.h` 里定义了两种上下文：

- `regs_context_t`：保存完整异常上下文，包括通用寄存器、`sstatus`、`sepc`、`sbadaddr`、`scause`。
- `switchto_context_t`：保存 `switch_to` 需要的被调用者保存寄存器。

PCB 里保存的是：

- `kernel_sp`：内核栈顶，用来恢复内核上下文。
- `user_sp`：用户栈顶，用来进入用户态后作为 `sp`。
- 进程状态、PID、等待队列、光标位置等。

这里的布局必须和 `arch/riscv/include/asm/regs.h` 中的偏移完全一致，因为 `entry.S` 里的 `SAVE_CONTEXT`、`RESTORE_CONTEXT`、`switch_to` 都是按固定偏移读写栈上的内容。

触发条件 -> 跳转依据 -> 下一站：

1. 条件
- 发生切换、异常返回或第一次启动用户进程。

2. 依据
- PCB 中保存的 `kernel_sp` 指向 `switchto_context_t`，其上方紧跟 `regs_context_t`。

3. 下一站
- `switch_to()` 或 `ret_from_exception()` 依赖这些上下文把 CPU 恢复到目标任务。

### 3.2 `init_pcb_stack()` 如何准备第一次切换

在 `init/main.c` 中，`init_pcb_stack()` 做了两件事：

1. 在内核栈上预留一块 `regs_context_t` 作为“异常返回上下文”。
2. 在它下面再预留一块 `switchto_context_t` 作为“调度切换上下文”。

流程是：

- `pt_regs = kernel_stack - sizeof(regs_context_t)`
- 清零后写入：
  - `pt_regs->regs[2] = user_stack`，也就是用户态 `sp`
  - `pt_regs->regs[4] = pcb`，也就是用户程序参数 `a0` 约定会看到的 PCB 指针
  - `pt_regs->sepc = entry_point`，下一条从哪里开始执行
  - `pt_regs->sstatus = SR_SPIE`，允许 `sret` 回到用户态后开启中断
- 再构造 `switchto_context_t`：
  - `ra = ret_from_exception`
  - `sp = switchto_context_t 自身地址`

最后：

- `pcb->kernel_sp = pt_switchto`
- `pcb->user_sp = user_stack`

### 3.3 `switch_to()` 的跳转依据

`arch/riscv/kernel/entry.S` 中的 `switch_to` 是任务 1 的核心。

它的逻辑可以理解成：

1. 把当前 CPU 的内核栈上保存当前任务的 callee-saved 寄存器。
2. 把当前 `sp` 写回当前 PCB 的 `kernel_sp`。
3. 从下一任务 PCB 取出 `kernel_sp`。
4. 把 `tp` 更新成下一任务的 PCB 地址，也就是 `current_running`。
5. 从下一任务的 `switchto_context_t` 恢复寄存器并跳回 `ra`。

跳转依据全部来自栈和 PCB 中保存的上下文，不是“函数调用返回值”意义上的 return，而是**通过恢复目标任务的寄存器现场来实现上下文切换**。

触发条件 -> 跳转依据 -> 下一站：

1. 条件
- 调度器决定从当前任务切到下一个 READY 任务。

2. 依据
- `switch_to(prev, next)` 通过 `a0/a1` 拿到两个 PCB，再用它们的 `kernel_sp` 保存/恢复上下文。

3. 下一站
- CPU 继续在 `next` 的内核上下文里执行，之后由 `ret_from_exception` 返回到用户态。

### 3.4 `do_scheduler()` 如何决定下一个进程

`kernel/sched/sched.c` 里的 `do_scheduler()` 负责从 `ready_queue` 中取任务。

典型逻辑：

- 先检查睡眠队列，唤醒已到期任务。
- 如果当前运行任务不是 idle，并且仍然是 RUNNING，就把它重新放回 ready queue。
- 从 ready queue 头部取出下一个 READY 任务。
- 设置其状态为 RUNNING。
- 调用 `switch_to(prev, next)` 真正切换。

如果 ready queue 空了，系统会让 CPU 回到 idle PCB，避免空跑。

触发条件 -> 跳转依据 -> 下一站：

1. 条件
- 时间片到期、任务主动让出、任务阻塞或被唤醒。

2. 依据
- `do_scheduler()` 检查 ready queue / sleep queue，并更新当前任务状态。

3. 下一站
- 选定的 `next_running` 进入 `switch_to()`，完成实际切换。

### 3.5 当前工程里为什么只启动 shell

`init/main.c` 里的 `init_task_info()` 定义了很多任务名，但为了避免启动阶段直接跑那些需要参数的测试程序，当前 `init_pcb()` 只装载 shell。

这意味着：

- 系统启动后先进入 shell。
- 之后所有 Project3 测试都是通过 shell 输入 `exec ...` 来启动。

这一步非常关键，因为很多测试程序要求命令行参数，否则会出现 `argc` 断言失败。

## 4. 任务 2：锁、屏障、条件变量、信号量、邮箱

### 4.1 自旋锁的基本原理

`kernel/locking/lock.c` 中，`spin_lock_t` 只有一个状态字段：`UNLOCKED` 或 `LOCKED`。

加锁时使用 `atomic_swap()`：

- 如果原值是 `UNLOCKED`，交换成 `LOCKED` 后获取成功。
- 如果原值已是 `LOCKED`，说明别的 CPU / 任务正在持有锁，当前任务继续自旋。

释放时再把状态写回 `UNLOCKED`。

触发条件 -> 跳转依据 -> 下一站：

1. 条件
- 多个任务同时访问共享资源。

2. 依据
- `atomic_swap()` 提供原子交换语义，决定当前任务是否能拿到锁。

3. 下一站
- 拿到锁则继续执行，拿不到则进入阻塞队列等待唤醒。

### 4.2 互斥锁 `do_mutex_lock_*`

互斥锁由两个部分构成：

- 一个底层自旋锁，保护锁对象本身。
- 一个阻塞队列，存放拿不到锁而睡眠的任务。

加锁流程：

1. 尝试抢自旋锁。
2. 如果失败，把当前任务放入互斥锁的阻塞队列。
3. 调用 `do_block()` 让出 CPU。
4. 被唤醒后再次尝试。

释放流程：

1. 解开自旋锁。
2. 如果阻塞队列非空，唤醒一个等待者。

### 4.3 屏障 `do_barrier_wait()`

屏障的本质是：**所有参与者都到齐之前，谁也不能继续往下走。**

流程：

1. 获取屏障自旋锁。
2. 如果当前到达人数还没到 `goal`：
   - `count++`
   - 释放锁
   - 当前任务阻塞到屏障队列
3. 如果已经是最后一个到达者：
   - 把 `count` 清零
   - 一次性唤醒队列里的所有等待者
   - 释放锁

因此你会看到多进程输出里，先是一批 “Ready to enter the barrier”，等全部到齐后才一起出现 “Exited barrier”。

触发条件 -> 跳转依据 -> 下一站：

1. 条件
- 某个参与屏障的任务调用 `sys_barrier_wait()`。

2. 依据
- 屏障记录到达人数 `count`，若未达到 `goal` 就把当前任务放入屏障队列。

3. 下一站
- 当最后一个任务到达时，统一唤醒之前被阻塞的任务。

### 4.4 条件变量 `do_condition_wait/signal/broadcast`

条件变量的核心思想是：

- 生产者和消费者共享一个互斥锁，保证共享状态一致。
- 等待条件时先释放互斥锁，再阻塞在条件队列上。
- 被唤醒后重新获取互斥锁，再检查条件。

在当前实现里：

- `do_condition_wait()`：先释放 mutex，再阻塞，再重新获取 mutex。
- `do_condition_signal()`：唤醒一个等待者。
- `do_condition_broadcast()`：唤醒全部等待者。

这正是 producer/consumer 测试的基础。

### 4.5 信号量

信号量本质上是一个整数计数器加阻塞队列：

- `down()`：如果值大于 0 就减一返回；否则阻塞。
- `up()`：值加一，并唤醒一个等待者。

### 4.6 邮箱 mailbox

邮箱用固定大小循环缓冲区保存消息，并配合发送队列、接收队列阻塞任务。

发送时：

- 如果缓冲区满了，发送者阻塞。
- 有空间后写入消息，必要时唤醒接收者。

接收时：

- 如果缓冲区空，接收者阻塞。
- 有数据后从队列中取出，必要时唤醒发送者。

这也是 `mbox_server` 和 `mbox_client` 能持续收发的原因。

## 5. 任务 3：系统调用、exec、argv 传递

### 5.1 用户态系统调用包装

`tiny_libc/syscall.c` 里，`invoke_syscall()` 用内联汇编把参数放进 RISC-V 约定的寄存器：

- `a0-a4`：前 5 个参数
- `a7`：系统调用号
- 执行 `ecall`

返回后，内核写回的结果仍然从 `a0` 取出。

`sys_exec()` 是一个变参封装，它把真正的参数整理成：

- `a0 = 程序名`
- `a1 = argc`
- `a2 = argv 指针`

### 5.2 内核怎么分发系统调用

`kernel/syscall/syscall.c` 中：

1. 从 `regs->regs[17]` 取出系统调用号，也就是 `a7`。
2. 用系统调用号查表 `syscall[fn]`。
3. 把 `a0-a4` 传给对应内核函数。
4. 把返回值写回 `regs->regs[10]`，也就是 `a0`。
5. `regs->sepc += 4`，让返回后跳过 `ecall` 指令。

这里的“跳过 4 字节”是因为 RISC-V 的 `ecall` 指令长度是 4 字节。

触发条件 -> 跳转依据 -> 下一站：

1. 条件
- 用户态执行 `ecall`。

2. 依据
- `syscall.c` 用 `a7` 找到系统调用号，再把 `a0-a4` 传给对应处理函数。

3. 下一站
- 处理完后更新 `a0` 和 `sepc`，由 `ret_from_exception` 返回用户态。

### 5.3 shell 如何触发 exec

`test/shell.c` 里，shell 的命令解析流程是：

1. 从串口逐字符读入一整行。
2. 以空白字符切分出 `argv_exec[]`。
3. 如果输入的是 `exec`：
   - `argv_exec[0] = "exec"`
   - `argv_exec[1] = 目标程序名`
   - `argv_exec[2...] = 程序参数`
4. 调用：
   `sys_exec(argv_exec[1], argc_exec - 1, &argv_exec[1])`

这就把 shell 的命令参数传给了内核。

触发条件 -> 跳转依据 -> 下一站：

1. 条件
- 用户在 shell 中输入 `exec xxx ...`。

2. 依据
- shell 把命令切成 argv 数组，并调用 `sys_exec()`。

3. 下一站
- 进入内核 `do_exec()`，开始构造新进程。

### 5.4 `do_exec()` 的真正工作

`kernel/sched/sched.c` 里的 `do_exec()` 是 P3 最关键的函数之一。

它做的事情可以概括成：

1. 按名字找到要运行的任务镜像 ID。
2. 找一个空闲 PCB。
3. 分配一页内核栈和一页用户栈。
4. 通过 `load_task_img(id)` 把目标程序装载到用户空间。
5. 在内核栈上构造 `regs_context_t` 和 `switchto_context_t`。
6. 设置用户态初始寄存器：
   - `sp` 指向用户栈顶
   - `sepc` 指向用户程序入口
   - `sstatus` 允许 `sret` 返回用户态
7. 把 argc/argv 放进用户程序约定的寄存器或用户栈中。
8. 把 PCB 放入 ready queue，等待调度器切换过去。

触发条件 -> 跳转依据 -> 下一站：

1. 条件
- shell 发起 `exec`。

2. 依据
- `do_exec()` 通过任务名找到镜像，分配内核栈/用户栈，并建立初始上下文。

3. 下一站
- 新 PCB 进入 ready queue，调度器随后切过去，用户程序开始运行。

### 5.5 用户程序怎么开始执行

`arch/riscv/crt0/crt0.S` 是用户程序的启动入口：

1. 清空 BSS。
2. 调用 `main()`。
3. `main()` 返回后调用 `sys_exit()`，避免程序直接掉出 `_start`。

所以真正的用户程序入口不是 `main` 代码本身，而是 `_start -> main -> sys_exit`。

### 5.6 以 add / multicore 为例的 argv 和结果传递

`test/test_project3/multicore.c` 的流程是：

1. 在一个固定地址构造 `TestMultiCoreArg`。
2. 里面包含：打印位置、from、to、result 指针。
3. 用 `itoa()` 把这个结构体地址转成字符串。
4. 通过 `sys_exec("add", 2, argv)` 启动 `add`，把地址字符串传进去。

`test/test_project3/add.c` 会：

1. 从 `argv[1]` 取出这个地址。
2. 把地址解析成 `struct TestMultiCoreArg *`。
3. 按 `from` 到 `to` 计算区间和。
4. 把结果写回 `args->result`。

这就是为什么前面如果没有“结果写回”，父进程看到的结果一直是 0。

**补充：代码之间的逻辑关系与栈/寄存器布局详解（为什么这样写）**

下面把重复出现在各处但容易被误解的“布局/顺序”问题讲清楚——尤其是 `do_exec()` 在内核栈上如何布置 `regs_context_t` 与 `switchto_context_t`、以及汇编中 `SAVE_CONTEXT`/`switch_to`/`RESTORE_CONTEXT` 之间如何协作恢复用户态寄存器。

一目了然的结论先给出：
- C 层在内核栈上按 `[switchto_context][regs_context]` 顺序布置数据；
- 汇编 `switch_to` 操作 `switchto_context`（快速保存/恢复 callee-saved）；
- 汇编 `SAVE_CONTEXT`/`RESTORE_CONTEXT` 操作 `regs_context`（保存/恢复全部用户寄存器及 CSR）；
- `do_exec()` 必须在 `pcb->kernel_sp + SWITCH_TO_SIZE` 处写入 `user_regs`（即 `regs_context_t`），以便 `RESTORE_CONTEXT` 能正确读取到 a0/a1/…，否则 `argc/argv` 等会被破坏。

下面逐步解释“为什么”以及“发生了什么”：

1) 两种上下文的职责不同（职责分离）
- `switchto_context_t`（在 C 中定义，大小为 `SWITCH_TO_SIZE`）：只保存内核级的 callee-saved 寄存器（例如 `ra, s0..s11`）和用于 `switch_to` 的最小必要信息。它用于快速在内核态不同 PCB 之间切换，不改变用户态的 `sepc/sstatus`。
- `regs_context_t`（在 C 中定义，大小为 `OFFSET_SIZE`）：保存完整的用户态寄存器集以及异常相关 CSR（`sstatus, sepc, sbadaddr, scause`）。它用于在异常/中断/系统调用发生时保存用户上下文，并由 `RESTORE_CONTEXT` 恢复到用户态（通过 `sret`）。

2) 为什么把 `switchto_context` 放在 `regs_context` 之下（栈更低处）？
- 设计目标：当 `switch_to` 发生时，我们只想快速保存/恢复少量寄存器并切换 `sp` 到下一个 PCB 的内核栈，而不要触及完整的用户寄存器快照（那会更慢、且在很多场景下不需要）。
- 因此内核栈的布局被设计为：
   高地址
   ...（kernel_stack 原顶）
   [ regs_context_t ]    <- 占用 OFFSET_SIZE 字节（完整用户寄存器保存区，用于 RESTORE/SAVE）
   [ switchto_context_t ] <- 占用 SWITCH_TO_SIZE 字节（切换时保存的 callee-saved）
   kernel_sp 指向 switchto_context_t 的起始（较低地址）
   低地址

   这样，当我们执行 `switch_to(prev, next)` 时：
   - `switch_to` 会在当前 `sp`（指向 prev.kernel_sp）上保存 callee-saved（填充 prev 的 switchto_context），并把 prev 的 kernel_sp 写回 PCB；
   - 然后加载 next.kernel_sp 到 `sp` 并恢复 next 的 callee-saved，从而让内核继续在 next 的内核栈上运行；
   - 如果 next 是新进程（其 kernel_sp 下方已经布置了 regs_context），恢复后 `ret` 的地址被设置成 `ret_from_exception`（由 `pt_switchto->regs[0]` 被设定），流程会跳到 `ret_from_exception` 执行 `RESTORE_CONTEXT`，最终 `sret` 到用户态入口（在 regs_context_t->sepc 中）。

3) `do_exec()` 在内核栈上按这个顺序构造数据的原因
- `do_exec()` 为新进程构造“可立即被调度并进入用户态”的内核栈镜像：
   - 它先在 kernel_stack 顶部写 `regs_context_t`，设置 sepc/sp/sstatus 等（使 `RESTORE_CONTEXT` 知道要返回到哪里）；
   - 在 `regs_context_t` 之下写 `switchto_context_t` 并把 `regs[0]` 设为 `ret_from_exception`（这样当 `switch_to` 返回时会跳到 `ret_from_exception`）；
   - 最后把 `pcb->kernel_sp` 指向 `pt_switchto`（switchto 的地址），以便 `switch_to` 能正确加载该内核栈。

   这个顺序保证了：
   - 调度器在后续 `switch_to(prev, next)` 时只需载入 `next.kernel_sp`，然后 `jr ra` 返回时会到 `ret_from_exception`，而 `ret_from_exception` 期望 `regs_context_t` 位于 `sp + OFFSET_SIZE`（或等效位置）并调用 `RESTORE_CONTEXT` 恢复完整用户寄存器。换言之，`switchto_context` 为了切换而存在，`regs_context` 为了恢复用户态而存在，两者配合完成“从内核进入用户态”的完整步骤。

4) 恢复路径（一步步，含寄存器变化）
- 场景：调度器选择了一个刚由 `do_exec()` 初始化的 PCB，并调用 `switch_to(prev, next)`。
   1. `switch_to` 保存 prev 的 switchto（callee-saved）并把 prev.kernel_sp 写回 PCB；
   2. `switch_to` 加载 next.kernel_sp 到 `sp`，并执行 `mv tp, a1` 将 `tp`（current_running）原子设置为 next；
   3. 恢复 next 的 callee-saved 并 `jr ra` 返回，此时 `ra` 指向 `ret_from_exception`（因为 `pt_switchto->regs[0]` 被设为该地址）；
   4. `ret_from_exception` 执行：把 `sp + OFFSET_SIZE` 存回 `PCB_KERNEL_SP(tp)`（维护 PCB 的 kernel_sp），然后执行 `RESTORE_CONTEXT`；
   5. `RESTORE_CONTEXT` 从内核栈中按照固定偏移读出 `sstatus/sepc` 并写回 CSR，再把全部通用寄存器恢复到 CPU 寄存器；
   6. 最后 `sret` 指令把 CPU 从特权态返回到用户态，PC 跳转到 `sepc`（即用户程序入口），用户寄存器（a0/a1 等）也已恢复为 `do_exec` 设定的值。

5) 为什么如果把顺序弄错会出错（举例）
- 常见错误一：把 `regs_context_t` 与 `switchto_context_t` 位置弄反或把 `user_regs` 写在错误偏移
   - 结果：`RESTORE_CONTEXT` 会从错误地址读出寄存器，导致 a0/a1（argc/argv）被污染或 sepc 被覆盖，用户程序收到错乱的参数或无法正确返回。
- 常见错误二：忽略对齐（例如 argv_area 未对齐到 16 字节）
   - 结果：有些用户程序（或 C 运行时）假设栈对齐，未满足时会出现不可预测行为。

6) 调试建议（实践中非常有效）
- 在 `init` 或 `do_exec` 打印并对比：`sizeof(regs_context_t)` 与 `OFFSET_SIZE`，`sizeof(switchto_context_t)` 与 `SWITCH_TO_SIZE`（见 [init/main.c](init/main.c#L74) 打印代码示例）。两两必须一致。
- 在 `do_exec` 写完 `user_regs` 后打印 `pcb[idx].kernel_sp`、`(ptr_t)pcb[idx].kernel_sp + SWITCH_TO_SIZE` 的地址与前后 16 字节内容（谨慎：不要直接 deref 用户地址，打印仅内核栈上已分配区域）。
- 如果用户看到 `argc == 0` 或 argv 错乱：优先检查 `user_regs` 的写入偏移是否等于 `pcb->kernel_sp + SWITCH_TO_SIZE`，以及 `SWITCH_TO_SIZE` 是否来自 `arch/riscv/include/asm/regs.h` 并与 `switchto_context_t` 的 sizeof 一致。

7) 代码间的因果链（简化图）
- shell -> sys_exec() -> ecall -> 异常入口 `SAVE_CONTEXT` 保存当前进程上下文 -> syscall 分发到 `do_exec()` -> `do_exec()` 在 kernel_stack 上写 `regs_context_t` & `switchto_context_t` -> 把 PCB 插入 ready_queue -> 调度器 `do_scheduler()` 选中该 PCB -> `switch_to(prev, next)` 完成内核栈切换 -> `ret_from_exception` -> `RESTORE_CONTEXT` -> `sret` -> 用户态 entry，a0/a1 已是 `do_exec` 写入的值。

8) 对比说明：什么时候只用 `switch_to` 而不触及 `regs_context`？
- 常见场景：内核内部线程切换（两个内核线程/内核态任务），它们共享相同的用户态环境或并非立即需要恢复用户寄存器。在这种情况下只需保存/恢复 callee-saved（`switchto_context`），无需完整用户上下文的开销。

## 6. 程序从头到尾的跳转依据

下面把最典型的执行链路串起来：

### 6.1 启动 shell

1. `init/main.c` 完成初始化。
2. `do_scheduler()` 选择 shell PCB。
3. `switch_to()` 切换到 shell 的内核栈。
4. `ret_from_exception()` 从用户上下文恢复。
5. `sret` 进入 shell 的用户态 `_start`。
6. `_start` 调用 shell 的 `main()`。

触发条件 -> 跳转依据 -> 下一站：

1. 条件
- 机器刚启动，内核完成初始化。

2. 依据
- 调度器选中 shell PCB，`switch_to()` 切换到它。

3. 下一站
- shell 的 `_start` 和 `main()` 接管用户态输入。

### 6.2 shell 执行 `exec multicore`

1. shell 解析命令行。
2. `sys_exec()` 触发 `ecall`。
3. `entry.S` 进入 `exception_handler_entry`，`SAVE_CONTEXT` 保存现场。
4. `kernel/syscall/syscall.c` 根据 `a7` 找到 `SYSCALL_EXEC`。
5. 分发到 `do_exec()`。
6. `do_exec()` 分配栈、装载镜像、准备 argv、构造上下文。
7. `do_exec()` 把新 PCB 放进 ready queue。
8. `sys_exec()` 返回 pid 给 shell。
9. 调度器切到新进程。
10. `ret_from_exception` -> `RESTORE_CONTEXT` -> `sret`。
11. 用户程序 `_start` 开始运行。

触发条件 -> 跳转依据 -> 下一站：

1. 条件
- shell 收到 `exec multicore`。

2. 依据
- 用户态系统调用进入内核，`do_exec()` 构造子进程上下文。

3. 下一站
- 调度器切到 multicore，随后 multicore 再次 exec 出 add。

### 6.3 multicore 再 exec 出 add

1. `multicore` 构造一组 `TestMultiCoreArg`。
2. 通过 `sys_exec("add", 2, argv)` 启动 `add`。
3. `do_exec()` 将 argv 字符串复制到新的用户栈。
4. `add` 进入 `main()` 后读取参数地址，计算区间和。
5. `add` 把结果写回 `args->result`。
6. `multicore` 等待子进程退出后读取结果并打印。

## 7. 你在测试里看到的现象该怎么理解

- `Info: execute xxx successfully, pid = N`：说明 `sys_exec` 成功创建了子进程。
- `start compute, from = ..., to = ... Done`：说明 `add` 收到了正确参数并完成计算。
- `single core: ... result = 630 / multi core: ... result = 630`：说明结果写回链路正确，两个线程/进程得到相同总和。
- `Ready to enter the barrier` / `Exited barrier`：说明屏障在“齐人之前阻塞，齐人之后放行”。
- `Total produced / Total consumed`：说明条件变量和互斥锁一起工作正常。
- `Client` / `Server` 的消息：说明邮箱的发送、接收、阻塞、唤醒都正常。
