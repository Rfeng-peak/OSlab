### 2.2 clear — 清屏

**命令**：
```
clear
```

**预期结果**：屏幕清空，光标回到左上角 (1,1)。

### 2.3 ps — 查看进程列表

**命令**：
```
ps
```

**预期输出**（示例）：
```
[Process Table]:
[0] PID : 1  STATUS : RUNNING
```

**验证点**：显示当前所有活跃进程的 PID 和状态（READY / RUNNING / BLOCKED / EXITED）。初始只有 shell（PID=1）处于 RUNNING 状态。

---

### 2.4 exec — 执行新进程 / getpid — 验证 PID 分配

执行任何 `exec` 命令启动新进程。每次执行后观察 PID 分配是否连续递增（从 2 开始，shell 的 PID=1）。

---

### 2.5 kill — 终止进程

**命令**：
```
exec waitpid 1 &       （启动 waitpid，若 shell 不支持 & 则略过）
ps                     （查看目标 PID，假设为 X）
kill X
```

**预期结果**：
- `kill X` 返回 `0`（成功终止）
- 对该 PID 再次执行 `kill X` 返回 `-1`（进程已退出）

**预期输出示例**：
```
> kill 5 -> 0
> kill 5 -> -1
```

---

### 2.6 互斥锁 + waitpid — `exec waitpid 1`

**命令**：
```
exec waitpid 1
```

**预期输出**：
```
> [TASK] I am task with pid 3, I have acquired two mutex locks. (XXXX)
> [TASK] I want to wait task (pid=3) to exit.
> [TASK] I want to acquire mutex lock1 (handle=0).
> [TASK] Task (pid=3) has exited.
> [TASK] I have acquired mutex lock1 (handle=0).
> [TASK] I want to acquire mutex lock2 (handle=1).
> [TASK] I have acquired mutex lock2 (handle=1).
> [TASK] I want to wait task (pid=4) to exit.
> [TASK] Task (pid=4) has exited.
```

**验证点**：
1. `ready_to_exit`（pid=3）获取锁1和锁2后进入循环
2. `wait_locks`（pid=4）尝试获取锁1时阻塞（因为被 pid=3 持有）
3. 父进程 kill pid=3 后，锁被释放
4. `wait_locks` 随后成功获取锁1和锁2
5. 父进程通过 waitpid 等待 pid=4 退出

### 2.9 邮箱 — `exec mbox_server 0` + `exec mbox_client`

**命令**：
```
exec mbox_server 0 &      （后台启动 server，若 shell 不支持 & 则先启动 server）
exec mbox_client            （启动 client 进行测试）
```

> 注：若 shell 不支持后台执行（`&`），则 `mbox_server` 会持续运行阻塞 shell。此时需确认测试策略（例如先在一个终端启动 server，再在另一个终端启动 client；或调整 shell 支持后台任务）。

**预期输出**：

Server 端：
```
[Server] server started
[Server]: received msg from <pid> (blocked: X, correctBytes: X, errorBytes: 0)
```

Client 端：
```
[Client] server started
[Client] send bytes: X, blocked: 0
```

**验证点**：
1. Server 首次收到 `clientInitReq` 后回复位置信息给 client
2. 后续消息由 Adler-32 校验，`errorBytes` 必须为 0
3. Client 发送随机长度的消息，Server 正确接收并校验

### 2.10 多核加速比 — `exec multicore 0`

**命令**：
```
exec multicore 0
```

**预期输出**（示例）：
```
start test multi-core performance
start compute, from = 0, to = 5000000  Done
single core: 784053 ticks, result = 630
start compute, from = 0, to = 2500000  Done
start compute, from = 2500000, to = 5000000  Done
multi core: 400000 ticks, result = 630
```

**计算公式**：加速比 = `single_core_ticks / multi_core_ticks`

**验证点**：
1. 单核和双核的 `result` 必须一致（均为 `630`），否则说明存在数据竞争
2. 双核加速比应 ≥ 1.5（`multi_core_ticks` 约为 `single_core_ticks` 的一半）

### 2.11 多核亲和性 — `exec affinity 0`

**命令**：
```
exec affinity 0
```

**预期输出**（示例）：
```
start test cpu affinity, pids = {3, 4, 5, 6, 7, }
[3] integer test (149/150) access: 2 auipc: 520b0082
[4] integer test (149/150) access: 3 auipc: 520b0082
[5] integer test (149/150) access: 5 auipc: 520b0082
[6] integer test (149/150) access: 1 auipc: 520b0082
[7] integer test (149/150) access: 7 auipc: 520b0082
```

**验证点**：
1. 所有进程的 `auipc` 值一致（`520b0082`），说明不同核心上地址空间一致
2. `access` 字段为合法索引值（"1", "2", "3", "5", "6", "7"），不会出现乱码
3. 在双核环境下，进程分布在两个核心上执行

## 三、常见问题排查

### 3.1 双核加速比不达标

**现象**：`multi core` 时间接近或大于 `single core` 时间。

**可能原因**：

1. **IPI 唤醒机制不工作**：检查 `send_ipi` → SBI `ecall` 是否能正确置位 MSIP，以及 `handle_irq_ssoft` 中是否正确清除 SSIP 并调用 `do_scheduler()`（当当前任务为空闲时）。

2. **大内核锁（BKL）竞争**：`do_scheduler()` 和 screen 操作中频繁 `lock_kernel()/unlock_kernel()` 导致两个核心互相等待。

3. **idle loop 的 wfi 竞态**：IPI 落在 `do_scheduler()` 返回和 `wfi` 之间的窗口时，若 SSIP 未能在 `wfi` 前到达，则核心可能睡过唤醒信号。当前修复方案：在 `handle_irq_ssoft` 中当 `current_running->pid == 0` 时直接调用 `do_scheduler()`，绕过 wfi 的竞态窗口。

**调试建议**：
- 在 `do_scheduler()` 中记录每个核心挑选的任务 PID
- 检查 `secondary_alive_flag` 是否为 `0xBEEF`

### 3.2 进程退出后 ps 仍显示

检查 `do_exit()` 是否正确将 `status` 设为 `TASK_EXITED`，以及 `do_kill()` 是否正确从 `ready_queue` 中移除 PCB。

### 3.3 锁/条件变量死锁

- 确保 `mutex_release` 仅由持有者调用
- 确保 `condition_wait` 在调用前已持有关联的 mutex
- 检查 `do_block()` 和 `do_unblock()` 是否正确操作链表
