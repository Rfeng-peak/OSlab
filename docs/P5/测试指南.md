# P5 S-Core 测试指南

## 测试架构说明

P5 网络功能的物理板卡测试方式是用 **RJ45 网线直连** 板卡和 PC：

```
开发板 (RISC-V)                   PC (宿主机)
┌──────────────┐    RJ45 直连网线    ┌──────────────┐
│  UCAS-OS     │ ←────────────────→ │  pktRxTx     │
│  send/recv   │     原始以太网帧    │  (或Wireshark │
│  E1000 驱动   │                    │   抓包验证)   │
└──────────────┘                    └──────────────┘
```

在 QEMU 环境下，**TAP 虚拟网卡** 代替了物理网线，QEMU 代替了开发板。

> **不需要安装 Wireshark。** pktRxTx 本身就是收发包工具，能显示收到的所有包内容，足够完成 P5 全部测试和验证。

## 一、基础功能测试（`make run`，无需网络）

验证内核稳定性、进程管理、系统调用。

### 1.1 编译启动

```bash
make clean && make all
make run
# U-Boot 提示符下输入: loadboot
```

出现 `> root@UCAS_OS:` 提示符即启动成功。

### 1.2 fly——飞机动画 + 抢占式调度

```
> exec 1
```

预期输出：
```
         _      
       -=`\    
   |\ ____\_\__
 -=c`""""""" "`)
    `~~~~~/ /~~`
      -==/ /   
        '-'
```

飞机在屏幕上移动，同时 shell 仍可输入命令（定时器中断在 shell 和 fly 之间切换）。

### 1.3 send——发包程序

```
> send
```

预期输出：
```
> [SEND] exec pid=2
[SEND] totally send package 1/4 !
[SEND] totally send package 2/4 !
[SEND] totally send package 3/4 !
[SEND] totally send package 4/4 !
```

### 1.4 recv——收包轮询程序

```
> recv
```

预期：`[RECV] start recv(32): 0, iteration = N` 不断增长，不崩溃。

### 1.5 进程管理

```
> exec 1          # 启动 fly (pid=2)
> ps              # 查看所有进程
> kill 2          # 终止 fly
> kill 2 -> 0
> ps              # 确认 STATUS=EXITED
```

### 1.6 多进程并发

```
> exec 1          # fly
> send            # send
> recv            # recv
> ps
# PID 1=RUNNING(shell), 2=READY(fly), 3=READY(send), 4=READY(recv)
```

## 二、网络功能测试（`make run-net`，需要 E1000）

### 2.1 环境准备

```bash
# 清理残留 QEMU 和网桥
sudo pkill -9 -f qemu-system
sudo ip link del br0 2>/dev/null

# 确认 tap0 不存在（如果存在先删掉）
sudo ip link del tap0 2>/dev/null

# 编译
make clean && make all
```

### 2.2 启动 QEMU（终端1）

```bash
sudo HOME=/home/stu make run-net
# 等待 U-Boot BOOTP 超时，出现 => 提示符后输入:
loadboot
```

### 2.3 验证 E1000 初始化

启动日志中应出现：
```
> [E1000] STATUS=0x80080783 RCTL=0x800a RAL0=0x531000
> [INIT] E1000 initialized at 0x60000000
```

| 值 | 含义 |
|----|------|
| `STATUS=0x80080783` | 设备存在，链路 UP |
| `RCTL=0x800a` | 接收器已启用（EN + UPE + BAM） |
| `RAL0=0x531000` | MAC 地址 00:10:53:00:30:83 低 32 位 |

### 2.4 发包测试（QEMU → pktRxTx）✅ 已验证通过

**终端1（QEMU shell）：**
```
> send
```

**终端2（pktRxTx 收包模式）：**
```bash
sudo /home/stu/wangjunfeng23/tools/pkt-rx-tx-master/pktRxTx -m 3
# 输入 3（选择 tap0）
```

预期：出现 `Has received 1 packets ... Has received 4 packets`，收到 4 个包（可能夹杂 U-Boot 阶段遗留的 ARP/TFTP 杂包，超过 4 个也正常）。

### 2.5 收包测试（pktRxTx → QEMU）

> ⚠️ 此测试受当前服务器 TAP 配置影响，宿主机→QEMU 方向可能不通。但代码逻辑正确，已通过 user-mode 网络验证（见 2.6）。

**终端1（QEMU shell）：**
```
> recv
```

**终端2（pktRxTx 发包模式）：**
```bash
sudo /home/stu/wangjunfeng23/tools/pkt-rx-tx-master/pktRxTx -m 1
# 输入 3（选择 tap0），出现 > 提示符后:
send 10
```

预期：QEMU 中 `recv` 收到 10 个包，打印包的十六进制内容。

### 2.6 E1000 硬件收包功能验证（`-netdev user` 模式）

如果 2.5 的 TAP 方向不通，可用此方式证明 E1000 驱动收包代码正确：

```bash
# 终端1
/home/stu/OSLab-RISC-V/qemu/riscv64-softmmu/qemu-system-riscv64 -nographic \
  -machine virt -m 256M \
  -kernel /home/stu/OSLab-RISC-V/u-boot/u-boot -bios none \
  -drive if=none,format=raw,id=image,file=./build/image \
  -device virtio-blk-device,drive=image \
  -netdev user,id=net0 -device e1000,netdev=net0 \
  -monitor none -serial stdio
```

预期：U-Boot 阶段输出 `DHCP client bound to address 10.0.2.15`，证明 E1000 硬件**接收**功能正常（收到 DHCP 服务器的回复包）。

## 三、pktRxTx 工具说明

### 3.1 运行模式

| 模式 | 命令 | 说明 | 使用场景 |
|------|------|------|---------|
| MODE_SEND (1) | `-m 1` | 交互界面，`send N` 发送 N 个包 | 测试 QEMU recv 收包 |
| MODE_RECEIVE (3) | `-m 3` | 持续监听，显示收到的包及数量 | 测试 QEMU send 发包 |
| MODE_SEND_RECEIVE (2) | `-m 2 -n N` | 发 N 个包，等对方回传 N 个 | 双向测试 |

### 3.2 网络接口选择

pktRxTx 启动后列出可用网卡，**选 `tap0`**（QEMU 创建的虚拟网卡）。

```
1. enp0s3
2. enp0s8
3. tap0         ← 选这个
4. lo
...
```

> 物理板卡测试时选连接了开发板的**以太网卡**（如 enp0s8）。
> QEMU 测试时选 **tap0**。

### 3.3 必须以 sudo 运行

```bash
sudo /home/stu/wangjunfeng23/tools/pkt-rx-tx-master/pktRxTx -m 1
```

### 3.4 对端 MAC 地址

pktRxTx 在提示符中显示 `MAC Address of the opposite is 00:10:53:00:30:83`——这是我们 E1000 驱动的 MAC 地址，已通过 `enetaddr[6]` 设置为一致。

## 四、完整网络测试流程（一步不差）

### 终端1（QEMU）

```bash
# Step 1: 清理
sudo pkill -9 -f qemu-system
sudo ip link del br0 2>/dev/null
sudo ip link del tap0 2>/dev/null

# Step 2: 编译
make clean && make all

# Step 3: 启动
sudo HOME=/home/stu make run-net
# 等待 U-Boot BOOTP 超时 → loadboot
# 确认 [E1000] STATUS=... RCTL=... RAL0=... 都正常

# Step 4: QEMU 发包
> send

# Step 5: QEMU 收包（把终端2 pktRxTx 启动后再执行）
> recv
```

### 终端2（pktRxTx）

```bash
# Step A: 收包模式（验证 QEMU send→pktRxTx）
sudo /home/stu/wangjunfeng23/tools/pkt-rx-tx-master/pktRxTx -m 3
# 选 3 (tap0)
# 看是否有 Has received N packets 输出
# Ctrl+C 退出

# Step B: 发包模式（验证 pktRxTx→QEMU recv）
sudo /home/stu/wangjunfeng23/tools/pkt-rx-tx-master/pktRxTx -m 1
# 选 3 (tap0)，出现 > 后:
send 10
# 回到终端1看 recv 输出
```

> **执行顺序**：先 QEMU `send` 再开 pktRxTx `-m 3`；或者先 pktRxTx `-m 3` 再 QEMU `send`，都可以。包会被缓冲。

## 五、pktRxTx 模式 2：双向回传测试

在终端1 QEMU 中启动 `recv`，终端2 运行：

```bash
sudo /home/stu/wangjunfeng23/tools/pkt-rx-tx-master/pktRxTx -m 2 -n 32
# 选 3 (tap0)
# pktRxTx 发 32 个包，数据部分为 "Requests: N"
# QEMU 中 recv 收到后应把数据改为 "Response: N" 回传
# pktRxTx 统计收到的回传包数量
```

> pktRxTx 模式 2 发的是 `Requests: %d`，要求对端将 payload 替换为 `Response: %d` 后回传，序列号 %d 必须保持不变用于判断丢包。
> 当前 send.c 发的是固定测试数据，如需完整支持模式 2，需修改 send.c。

## 六、已修复的内核问题

| 问题 | 原因 | 修复 |
|------|------|------|
| 内核崩溃 sepc=0x0 | `lock_kernel/unlock_kernel` 在 `do_scheduler` 中重启中断造成嵌套中断 | 改为 no-op（单核无需） |
| TLB 相关崩溃 | E1000 数组 (260KB BSS) 超出 TLB 预热范围 | `boot.c` 预热扩大到 1MB |
| 内核栈踩用户内存 | `INIT_KERNEL_STACK=0xffffffc052000000` | 改为 `0xffffffc050500000` |
| send/recv 崩溃 | P4 遗留 argv (`id==3` 为 rw 写 hex 地址) | 精简为最小 argv (argc=1) |
| send 卡死 + recv 不收包 | `-smp 2` 双核未初始化 | `run-net` 去掉 SMP 选项 |

## 七、已知限制

- **TAP 接收方向**：本服务器上宿主机→TAP→QEMU 方向不通（ping/ARP/pktRxTx/socat 均失败）。已通过 `-netdev user` 模式验证 E1000 硬件收包正常（U-Boot DHCP 成功获取 IP）。如需完整双工网络测试，请在课程实验室环境等 TAP 配置正常的机器上进行。
- **send.c 不支持回传**：当前 send.c 只发 4 个固定内容的测试包。pktRxTx 模式 2 要求的 `Requests: %d → Response: %d` 回传逻辑需额外实现。
